# 카드 결제 예약 만료·장애 복구 안전성

작성일: 2026-09-16. 범위는 서버 코드와 격리된 PostgreSQL 시험이다. 실제 Render 배포·원본 DB 백업·실 PG 결제·PortOne 연결 완료 보고서가 아니다.

## 수정한 경계

GP 구매와 카드 결제 준비는 사용자 행 다음 박스 행을 잠그고 총 판매량과 결제 예약량을 확인한다. 그러나 기존 카드 승인 시작 경로는 사용자 행만 잠그고 애플리케이션 시각 `Date.now()`로 예약 만료 여부를 판단했다.

따라서 DB에서는 만료되어 다른 고객이 구매한 수량을 서버의 느린 시각이 아직 유효하다고 판단하거나, 결제 행 잠금 대기 중 만료되었는데 잠금 대기 전의 판단으로 승인을 시작할 수 있었다. 기존 GP-only 50명 시험은 이 경계를 검증하지 않는다.

`PaymentsService.confirm()`은 이제 다음 순서를 따른다.

1. 사용자 행 잠금과 소유권 확인.
2. 해당 박스 행 잠금. GP 구매·다른 카드 예약과 같은 수량 직렬화 지점이다.
3. 결제 행 잠금 후 상태를 다시 읽는다.
4. 금액·거래번호와 기존 확정·진행 상태를 확인한다.
5. 신규 승인에 한해서 모든 잠금 대기가 끝난 뒤 DB `clock_timestamp()`로 만료를 재검사한다.
6. 유효한 예약만 CONFIRMING으로 기록하고 DB 트랜잭션을 커밋한다.
7. 외부 공급자 호출은 DB 잠금 밖에서 실행한다. UNKNOWN 재호출이나 승인 중복 전송은 허용하지 않는다.

이미 APPROVED 또는 PAID인 결제는 예약 만료를 이유로 취소하지 않는다. 승인 후 지급 실패 복구는 이미 승인된 결제의 지급만 재시도한다. CONFIRMING·UNKNOWN·APPROVED는 계속 예약 수량으로 계산한다.

공식 근거: https://www.postgresql.org/docs/17/explicit-locking.html 및 https://www.postgresql.org/docs/17/functions-datetime.html . `clock_timestamp()`는 트랜잭션 시작 시각과 다르게 호출 당시 시각이다. 이번 변경은 실제 사용하는 PostgreSQL 16 및 18 CI에서 검증한다.

## 시험과 증거

`test/payment-reservation.postgres-spec.ts`는 외부 PG가 아닌 모의 공급자와 로컬 PostgreSQL만 사용한다. 접속 대상은 127.0.0.1의 전용 시험 DB로 고정한다. 신규 시험은 다음 7개다.

- DB에서 만료된 예약과 마지막 수량 판매 후 서버 시각 지연을 재현. 추가 주문·공급자 호출 금지.
- 별도 연결이 결제 행을 잠가 승인을 실제 대기시키고 예약 만료 후 대기를 해제. 만료 재검사와 다른 고객 구매 결과 확인.
- 서로 다른 50명: 카드 예약 25건 + GP 구매 25건. 예약과 확정 구매 합계는 정확히 1. 실패 사유와 GP 총잔액 확인. 이 검사는 서비스 호출 경쟁이며 HTTP 성능 측정이 아니다.
- 승인 응답 지연과 UNKNOWN: 만료 이후에도 예약 유지, 승인 재전송·임의 취소·추가 판매 금지.
- 준비 중 결제를 6번 취소해도 같은 취소 결과. 취소 후 늦은 승인 요청이 재고를 되살리지 않음.
- 승인 후 캡슐 기록 실패를 DB 트리거로 주입. 지급 트랜잭션 롤백, APPROVED 유지, 재시도 6회에 주문·캡슐 1개와 공급자 승인 1회, GP 차감 없음.
- 다른 사용자와 금액 불일치 요청은 공급자 호출 전에 거절.

`tools/release/payment-regression.cjs`는 임시 CI 작업 디렉터리에서만 실행하는 전후 대조 도구다. 기준 커밋 `ec899c7ad28b1e46056850868f98fba1cdb6ac05`의 결제 서비스만 임시로 복원하여 앞의 두 시험을 실행한다. 실패 코드만 보는 것이 아니라 컴파일/런타임 오류가 없고 지정한 두 assertion이 실패했는지 검사한다. 시각 지연 사례에서는 재고 1개에 주문 2개가 만들어졌는지, 행 잠금 대기 사례에서는 만료 승인이 잘못 허용됐는지 확인한다. 이후 현재 코드를 복원하고 7개 전체가 통과해야 대조 검증 성공이다.

반드시 해당 최종 커밋의 GitHub Actions 결과와 다음 산출물을 확인한다. 파일 존재나 소스 검토만으로 통과라고 판정하지 않는다.

- `payment-before.json`, `payment-before.log`: 기준 코드의 의도된 실패 기록.
- `payment-after.json`, `payment-after.log`: 수정 코드 시험 결과.
- `payment-regression.json`: 두 실패 원인과 수정 후 결과를 검증한 요약.
- 기존 `report.json`, `execution.log`: 합성 백업·복원·6→15개 마이그레이션·50명 HTTP GP 구매 리허설.

이전 합성 리허설 결과만 복사해 신규 검증 결과로 취급하지 않는다. PostgreSQL 16 일반 검사와 PostgreSQL 18 리허설이 모두 최종 코드에서 완료돼야 한다.

## 변경하지 않은 영역

API 경로·요청/응답 구조, 확률 스냅샷, 실제 추첨 확률, 상품별 실물 재고, 배송비, GP 환산율, 운영 결제 게이트는 바꾸지 않았다. DB 마이그레이션을 추가하지 않았다. PortOne 어댑터·실 PG 조회/대사·환불 추가 구현도 이번 변경 범위가 아니다.

서버의 checkout 화면 준비 단계에는 여전히 앱 서버 시각을 쓰는 유효성 검사가 있지만, 상품 지급을 허용하는 최종 confirm 경계는 DB 시각·행 잠금으로 검사한다. 실 PG 운영화 시 checkout UX와 승인·조회·취소 전체 계약을 함께 검수해야 한다.

## 실제 배포에 남은 일

1. 원본 DB의 보호된 백업을 확보하고 별도 DB에서 복원 가능성을 검증한다. 이번 CI 합성 백업은 원본 백업을 대신하지 않는다.
2. 실제 대상 서버·DB와 배포할 커밋을 확정한다. 기존 자동배포 브랜치와 시작 명령에 들어 있는 시험 데이터 준비 단계를 정리해야 한다.
3. 단일 배포 실행자만 DB 변경을 적용하고, 동일 커밋을 실행해 /health/ready를 확인한다. 이번 수정은 이 절차를 실행한 것이 아니며 마이그레이션 전용 잠금 도구도 추가하지 않았다.
4. 사용자 권한·기존 거래 복구·시험 계정의 앱/관리자 연계를 확인한다. 증거 없이 운영 제한을 해제하지 않는다.
5. 실제 PG·확률/실물 공급·배송/전환/환불·스토어 검토는 별도 출시 인수조건으로 유지한다.

이 문서와 시험 코드를 공개 PR에 올리는 과정에서 실제 고객 데이터, 비밀번호, DB 접속 문자열 또는 공급자 비밀 키를 포함하지 않는다.
