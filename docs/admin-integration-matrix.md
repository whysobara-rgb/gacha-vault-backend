# 관리자와 고객 앱 연동·추적성 명세

2026-09-15. 동일 서버/DB를 사용하는 개발·시험 환경의 구현 명세다. 공개 관리자 웹은 연습 모드로 시작한다. 공개 주소만으로 운영 서버가 배포되거나 관리자 권한이 부여되지 않는다.

## 지원 범위

| 업무 | 관리자 입력/조회 | 고객 웹·휴대폰 반영 | 기록·보호 |
|---|---|---|---|
| 상품·카테고리·가격·구성·개별 확률 | `/ops/catalog/:id/draft`, `/publish`, `/availability` | `/gachas`, `/gachas/:id`, `/gachas/:id/odds` | 초안/적용/판매 구분, 버전 충돌 거절, 기존 주문 스냅샷 불변 |
| 홈 배너·기획전 | `/owner/campaigns` + `/draft` + `/status` | 공개 `/campaigns`; 홈 노출 체크된 상위 5개 | 공개 상태·시작/종료 시각·박스 판매 상태, HTTPS 이미지, 내부 예산 비공개 |
| 공지·알림 | `/ops/announcements`, 배송·상담 상태 처리 | `/announcements`, `/notifications` | 공지 게시/보관, 고객 알림 소유권·읽음 |
| 주문 추적 | `/owner/orders/:id`, `/owner/trace?kind=...&reference=...` | 고객 본인 주문·보관함·배송·문의 번호와 대조 | 주문 → 캡슐 → 불변 개봉 → 보관 번호 → SKU → 배송/전환/문의 |
| 실물 재고 | `/ops/warehouse/skus`, `/movements`, `/items/:id/link` | 판매 상품 SKU 및 배송 가능 조건 | 실사·입고·예약/출고, 요청 결과 대상번호 검증 |
| 예전 준비 건 예약 보완 | `/ops/warehouse/fulfillments/:id/reserve` | 해당 배송·실물 예약 | 준비 상태·버전·미연결/부족 재고 검사 |
| 배송·운송장 | `/ops/fulfillments/:id/status` | `/fulfillments` 및 `/:id` | REQUESTED → PREPARING → COLLECTED → SHIPPING → DELIVERED; 실제 인계 후 입력 |
| 배송 신청/취소 | 고객 `/fulfillments/quotes`, `/fulfillments`, `/:id/cancel` | 웹·앱 서버 견적/주소/수량, 상태·택배사·운송장 | 같은 요청번호 재시도, 집화 전 취소/GP 환급, 원장/실물 예약 동시 처리 |
| 고객 문의 | `/staff/support/tickets/:id/messages`, `/status` | `/support/tickets`, `/:id`, `/messages` | 주문 소유권, 메시지 순서, 앱 암호화 전송 복구 |
| 반품·교환·파손 조치 | `/owner/cases`, `/:id` | 본인 `/support/cases` | 공개 안내 vs 내부 메모/참조 분리, 버전 검사, 종료 근거, 자동 금전/재고 이동 없음 |
| 발주·부분 입고 | `/owner/procurements`, `/:id/status` | 창고 가용 재고·출고 준비 | 공급처 주문은 외부 수행; 입고 검수와 원장 반영은 한 트랜잭션 |
| 비상 판매 중지 | `/owner/pause-sales` | 신규 구매 가능 여부 | 기존 거래 유지, 중지 요청·작업자 기록 |

## 반영 규칙

- 관리자 초안 저장만으로 고객 화면은 바뀌지 않는다. 상품 적용·판매 시작, 이벤트 공개·기간 도래, 공지 게시를 끝내야 한다.
- 고객 웹 새 조회, 앱 홈 재진입/당겨 새로고침, 배송 상세 새로고침에서 최신 서버 결과를 가져온다. 웹소켓 실시간 동기화가 아니다.
- 구매 확인 후 가격·확률이 바뀌면 서버가 오래된 구매 확인 요청을 거절한다. 이미 구매된 주문의 확률·개봉 결과는 바뀌지 않는다.
- 숫자 보관번호를 제외한 추적 입력은 전체 UUID다. 서로 다른 주문의 상품이 함께 배송/전환되면 원주문이 여러 개 조회된다. 합배송 전체 금액을 개별 주문 매출처럼 합산하지 않는다.
- 주문 추적은 직접 연결 이력이며 고객 전체 접속/행동 분석이 아니다. 관련 기록은 최대 200개까지 표시하고 잘림을 명시한다. 전체 내용은 각 업무 상세·페이지에서 확인한다.
- 앱은 동일 서버의 API_BASE_URL로 빌드해야 한다. 서버 기능 게이트와 계정 권한, DB 15개 마이그레이션이 선행된다. 개발용 ENABLE_SHIPPING_PREVIEW 플래그는 release 빌드 거래를 허용하지 않는다.

## 검증 기준

- SQL: 동일 요청 재시도, 내용 불일치, 고객/관리자 경계, 같은 주문의 문의 연결, 내부 필드 비공개, 조치 종료 근거/다시 열기, 안전한 배너 이미지.
- PostgreSQL HTTP: 전체 관리자 등록·구매·개봉·배송·문의·조치 흐름과 실제 JWT 인증·응답 포맷. 테스트용 상품·계정·환불 달력만 사용한다.
- 웹: 실제 DOM 이벤트 핸들러를 호출하는 어댑터 검사. 주문·조치·SKU 연결·직접 입고 및 복구 화면, 공개/중지 배너 반영을 검사한다. 브라우저 시각 검수는 별도다.
- 앱: 서버 공개 콘텐츠 파싱, 100개 초과 상품 페이지 조회, 배송 6개 상태·운송장, 서버 견적 사용, 분실 응답·재시작·계정 분리·저장 실패, 다른 금액/다른 대상 응답의 복구 기록 유지.

## 관리자에서 아직 직접 실행하지 않는 업무

카드 가격 변경·PG 실제 승인/취소/대사·운영자 환불, 자동 송장/추적/수거, 교환 상품 재지급, 쿠폰·자동 보상·GP 마켓·A~K 확률 그룹, 배송비/GP 정책 편집, 관리자 MFA·본인/연령 확인·최종 탈퇴/보존, 계약/정산/회계·외부 메일/문자/푸시, 서버 배포·비밀키·백업/복원/부하 경보는 별도 출시 작업이다. 현재 조치 기록만으로 이를 완료했다고 표시하지 않는다.
