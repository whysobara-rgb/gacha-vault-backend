# 1인 운영실 — 구현 계약과 서버 연결

2026-09-15. 별도 웹 진입점: https://gachigacha-studio-preview.bara3840.chatgpt.site/admin.html

이 PR은 소스와 검사를 제출한다. 상용 DB 적용, 계정 권한 부여, 실제 PG 승인·정산 또는 앱 출시를 완료했다는 뜻이 아니다. 콘솔은 기본적으로 기기 내 연습 모드이며 실제 계정 연결은 명시적으로 선택한다.

## 최초 연결

1. 격리된 테스트 환경에 PR의 서버 빌드와 전체 마이그레이션 14개를 적용한다. `synchronize`는 끈 상태로 유지한다.
2. 본인 이메일로 기존 회원가입·로그인을 진행한다. DB에서 본인이 확인한 **기존 계정 ID와 정확히 일치하는 이메일**을 사용한다. 관리자 자동 가입/기본 비밀번호/공개 권한 부여 API는 없다.
3. 서버의 기존 DB 환경 설정으로 `npm run owner:access -- --user-id 123 --email owner@example.invalid --action grant`를 실행한다. 이 예시 ID/이메일은 바꿔야 한다. 기본값은 조회만 하는 dry run이다.
4. 대상과 작업을 확인한 뒤 같은 명령 끝에 `--apply`를 붙인다. OWNER, CATALOG, FULFILLMENT, WAREHOUSE, ANNOUNCEMENTS 및 상담 권한이 트랜잭션으로 적용되고 기존 토큰은 회수된다. 다시 로그인해야 한다. 실행자의 인프라 접속 기록은 별도 보존한다.
5. `NODE_ENV=test` 또는 `development`, `ENABLE_OPERATIONS_PREVIEW=true`, `ENABLE_LEGACY_TRANSACTIONS=false` 조건에서만 변경이 허용된다. 기능을 켜기 위해 운영 환경을 테스트로 위장하지 않는다. 상용 모드 전환과 운영 심사는 별도 출시 작업이다.
6. 운영실 → 서버 연결에서 로그인한다. `/owner/capabilities`의 OWNER 권한과 `OWNER_CONSOLE_V1` 계약을 확인한다. CORS에는 기존 공개 웹 원점을 허용해야 한다. 연결 실패는 연습 데이터로 대체 표시하지 않는다.
7. 폐기/침해 시 `--action revoke --apply`로 운영·상담 권한과 세션을 회수한다. 2단계 인증·관리자 전용 세션/접속 통제는 출시 전 추가해야 한다.

## 기능 범위

| 메뉴 | 지원 | 남은 실제 운영 작업 |
|---|---|---|
| 오늘 할 일 | 배송·문의 지연, 부족 재고, 발주 지연, 결제 확인, 최근 7일 주문 | 외부 경보, 고객 유입 분석, 실제 순이익 |
| 상품·확률 | GP 박스 초안·검토·적용·판매 시작/중지, 개별 확률 합계 검증 | 카드 박스 편집, 그룹 확률/보장형 엔진 |
| 발주·입고 | 공급처·참조번호·단가·납기, 주문 기록, 부분/전체 입고 | 공급처 주문·결제는 외부에서 수행; 반품/발주 변경 별도 |
| 실물 재고 | SKU·입고·조정·예약·출고 원장 | 구매·개봉 결과의 전체 지급 의무 보장, 자동 조달 |
| 배송·문의·공지 | 기존 검증 API에 연결; 상태 순서·운송장·답변·게시 | 자동 송장/추적, 반품·교환·분실, 외부 발송 |
| 이벤트 | 기획전/안내의 초안·예약 공개·중지·보관 | 쿠폰·자동 보상·할인·랭킹 페이백 |
| 결제 확인 | 미확정 승인/환불을 페이지별 조회 | PG 조회·대사·운영자 환불·복구, 영수증 |
| 원가·마진 | 확률 가중 매입 원가·비용·광고비·처리량 가정 계산 | 실제 회계, GP 재사용·상품 의무/현금흐름 모델 |
| 통제실 | 현재 등록된 신규 박스 판매 일괄 중지·감사 기록 | 기존 주문 취소가 아니며, 나중에 박스별 재개 가능 |
| 탈퇴 요청 | 요청 목록 확인 | 최종 삭제·의무 보존 분리 |

공개 `/campaigns`는 기간 내 공개 승인된 기획전/안내만 반환한다. 연결 박스가 중지되면 기획전을 숨긴다. 내부 예산·버전·운영 기록·개인정보는 포함하지 않는다. 고객 웹의 이벤트 메뉴에서 확인한다. 네이티브 이벤트 화면은 별도 통합 작업이다.

## 중복·동시 변경의 보호

- OWNER 검사와 현재 사용자 auth_version을 읽는다. 변경 시 사용자·권한·업무 행을 잠그고 권한을 다시 확인한다.
- 발주 생성·입고·이벤트·판매 중지는 기존 운영 요청 원장에 요청키+내용 해시+최종 응답을 보존한다. 같은 키/내용 재시도는 이전 결과를 반환한다.
- 입고 검수는 발주 버전 확인과 재고 원장 반영이 같은 트랜잭션이다. 미입고 수량 초과, 입고 후 취소, 다른 버전 중복 입고를 거절한다.
- 브라우저는 전송 전 요청키와 대상을 저장한다. 응답 유실 시 원요청 조회/동일 요청 재시도로 복구한다. 대상이 다른 응답은 완료로 처리하지 않는다. 관리 세션은 고객 세션과 별도로 저장한다.
- 확률 변경은 이후 구매부터 적용하고 과거 주문의 상품/확률 스냅샷을 보존한다. 유한 재고 추첨이나 상품 보장 확률 정책으로 간주하지 않는다.
- 운영 기록은 앱에서 삭제하지 않는다. 스키마 되돌리기도 기록이 있으면 거절한다.

## 검증

`npm run check:types`, `npm run build`, `npm test -- --runInBand`.
격리 PostgreSQL 16 CI에서 마이그레이션 후 `npm run test:postgres`.
신규 검사: HTTP 인증·입력 경계 4개, SQL/권한 부여·회수·발주·이벤트·판매 중지 7개, PostgreSQL 다중 연결 입고/이벤트 경쟁 3개.
실제 PG·공급처·택배·실기기·부하 검증은 포함하지 않는다.

## 사업·스토어 출시 판단

1인 운영 편의성만으로 수익성이 검증되지 않는다. 실제 원가·수수료·배송·반품·CAC·고객 재구매, GP 전환/재사용과 상품 지급 의무를 함께 검증해야 한다. 자동 매출 보장이나 고객 지출 유도 장치는 구현 목표가 아니다.

유료 무작위 실물 보상/GP 구조는 스토어·PG 적합성 확인이 선행되어야 한다. Google Play의 [실제 돈을 사용하는 도박/게임 정책](https://support.google.com/googleplay/android-developer/answer/9877032?hl=en)은 실제 돈 또는 구매 재화로 실제 가치의 보상을 얻는 비승인 구조를 제한한다. [Apple 심사 지침](https://developer.apple.com/app-store/review/guidelines/)의 실물 상품 결제 규정만으로 무작위 유료 상품 전체가 승인된다고 판단하지 않는다. 구체적 판매 모델·환급/전환·보상 구조를 기준으로 확인한다.
